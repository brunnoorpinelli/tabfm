TabFM no BigQuery3
Conceito

TabFM: um foundation model para tabelas

Desenvolvido pelo Google Research e pré-treinado em enorme variedade de problemas tabulares. Faz classificação e regressão sem ajuste de parâmetros.

In-context learning, como em um LLM

Um LLM aprende uma tarefa a partir de exemplos no prompt (few-shot). O TabFM lê sua tabela histórica como exemplos em contexto e gera previsões para a tabela alvo em um único passo.

Não existe fase de treino. O "modelo" é o próprio par (dados rotulados, dados a prever) que você passa na query.

Características

  • Zero-shot: sem treino, tuning ou deploy
  • Featurização automática: nulos, categóricas, escalas
  • Tarefa inferida pelo tipo do rótulo: BOOL/STRING → classificação; numérico → regressão
  • Estado da arte no benchmark TabArena, à frente de modelos clássicos e de outros foundation models tabulares
  • Nativo do BigQuery: SQL, governança e escala do warehouse

Amostragem inteligente

Se o histórico é grande, o BigQuery seleciona automaticamente os exemplos em contexto, respeitando o orçamento de memória do modelo.

Execução paralela

A inferência é distribuída pelos slots: milhões de linhas de predição em minutos, sem runtime para operar.

Só SQL

Funciona em queries, views, table functions, scheduled queries, Dataform e via BigQuery MCP server para agentes.

TabFM no BigQuery5
Sintaxe

AI.PREDICT: classificação de fraude em uma query

SELECT *
FROM AI.PREDICT(
  -- 1) exemplos rotulados (in-context)
  (SELECT * EXCEPT(transaction_id, customer_id, transaction_ts)
   FROM `proj.fraude.transactions`
   WHERE transaction_ts < '2026-07-01'),
  -- 2) linhas a prever
  (SELECT * FROM `proj.fraude.transactions`
   WHERE transaction_ts >= '2026-07-01'),
  -- 3) coluna alvo (default: 'label')
  label_col => 'is_fraud'
);

Regras que importam

  • Toda coluna do treino que não é o rótulo vira feature. Retire IDs e timestamps com EXCEPT.
  • A tabela de predição precisa ter todas as features; pode ter colunas extras (IDs, rótulo real para avaliar).
  • Tipos aceitos: STRING, BOOL, INT64, FLOAT64, NUMERIC, BIGNUMERIC. Derive hour_of_day a partir de TIMESTAMP.
  • Aceita TABLE nome ou (subquery) nos dois argumentos.

Saída

O que a função devolve

ColunaTipoQuando
colunas da tabela de prediçãooriginaissempre
predicted_<label>mesmo tipo do rótulosempre
predicted_<label>_probsARRAY<STRUCT<label STRING, prob FLOAT64>>classificação

Rótulo BOOL gera labels 'true'/'false' no array de probabilidades.

Extrair a probabilidade de fraude

SELECT
  transaction_id,
  predicted_is_fraud,
  (SELECT p.prob
   FROM UNNEST(predicted_is_fraud_probs) p
   WHERE p.label = 'true') AS fraud_prob
FROM AI.PREDICT(...);

A probabilidade permite calibrar o limiar pela capacidade da mesa de análise, em vez de aceitar o corte padrão de 0,5.

TabFM no BigQuery7
Sintaxe

AI.EVALUATE: qualidade com a mesma assinatura

SELECT *
FROM AI.EVALUATE(
  (SELECT * EXCEPT(transaction_id, customer_id, transaction_ts)
   FROM `proj.fraude.transactions`
   WHERE transaction_ts < '2026-07-01'),
  (SELECT * EXCEPT(transaction_id, customer_id, transaction_ts)
   FROM `proj.fraude.transactions`
   WHERE transaction_ts >= '2026-07-01'),
  label_col => 'is_fraud'
);

A segunda tabela precisa conter o rótulo real. label_col é obrigatório no AI.EVALUATE.

Classificação

precision · recall · accuracy · f1_score

Regressão

mean_absolute_error · mean_squared_error · mean_squared_log_error · median_absolute_error · r2_score · explained_variance

Boa prática: split temporal (treino no passado, avaliação no período seguinte) para não superestimar o resultado.

Exemplos em instituição financeira

  • Classificação: fraude, churn, inadimplência (default), propensão a produto, contestação de chargeback, classificação de transações (até 10 classes)
  • Regressão: LTV, valor esperado de perda, limite de crédito recomendado, ticket médio futuro, tempo até chargeback

Cuidado com vazamento: retire do treino colunas derivadas do rótulo (ex.: amount_to_avg_ratio ao prever amount).

TabFM no BigQuery9
Por que importa

Cinco vantagens

1 · Zero-shot

Da pergunta à previsão em uma query. Sem pipeline de treino, sem endpoint, sem re-treino agendado.

2 · Acurácia de ponta

Supera modelos tradicionais treinados sob medida em datasets complexos (TabArena). Featurização e tratamento de nulos automáticos.

3 · Experiência simples

Quem sabe SQL faz ML preditivo. Democratiza para analistas, engenheiros de dados e times de negócio.

4 · Escala do BigQuery

Inferência distribuída: milhões de linhas em minutos, dentro do perímetro de segurança e governança do warehouse.

5 · Pronto para agentes

Via BigQuery MCP server, um agente responde "quais clientes têm maior risco?" chamando AI.PREDICT como ferramenta.

Complementa, não substitui

Convive com BOOSTED_TREE, LOGISTIC_REG, AutoML e Vertex AI. O ganho é tempo até o valor e custo operacional.

Demo · adaptação

Golpe novo? Mude a janela do WHERE, não o modelo

Comparamos duas execuções sobre o mesmo julho, mudando só a janela de treino:

-- desatualizada
WHERE transaction_ts < '2026-06-01'
-- atual (inclui junho, quando o padrão surge)
WHERE transaction_ts < '2026-07-01'

Nenhum re-treino, nenhum deploy. Em produção: janela deslizante em uma view ou scheduled query.

Escolhendo a ferramenta

Quando escolher cada um

TabFM

  • Previsão rápida sem time de ML
  • Histórico pequeno ou médio
  • Dados mudam com frequência (fraude, campanhas, estoque)
  • Muitos problemas pequenos (um por produto, região, segmento)
  • Agentes e fluxos conversacionais que pedem previsão sob demanda
  • Prototipar em horas antes de investir em um modelo dedicado

BQML treinado

  • Mais de 20 features ou mais de 10 classes
  • Volume de treino muito grande
  • Precisa de importância de features (auditoria, regulador)
  • Quer controlar hiperparâmetros e reproduzir versões
  • Séries temporais (ARIMA_PLUS, AI.FORECAST/TimesFM), clustering, recomendação

Vertex AI

  • Inferência online com latência de milissegundos (autorização em tempo real)
  • Arquiteturas customizadas, deep learning, dados não tabulares
  • MLOps completo: pipelines, registry, monitoramento de modelo
Linhas rotuladas na janela de treinoLeitura prática
até ~150 milFaixa validada no benchmark TabArena (700 a 150 mil linhas). TabFM tende a igualar ou superar modelo treinado.
150 mil a alguns milhõesFunciona, mas o treino é amostrado automaticamente. Compare AI.EVALUATE × ML.EVALUATE antes de decidir.
dezenas de milhõesModelo treinado aproveita melhor o volume. TabFM ainda útil para prototipar e para agentes.

Não há número oficial para "pequeno a médio"; a faixa acima vem do benchmark usado pelo Google. O que conta é a janela passada na query, não o tamanho da tabela: em fraude, 90 a 180 dias com todas as fraudes e legítimas amostradas costuma caber na faixa validada.

Padrão recomendado: TabFM para scoring em lote, triagem e novos padrões; modelo treinado/online para bloqueio em tempo real na autorização.

Operacionalização

Scheduled query diária com janela deslizante

CREATE OR REPLACE TABLE `proj.fraude.scores_d1` AS
SELECT transaction_id, predicted_is_fraud,
  (SELECT p.prob FROM UNNEST(predicted_is_fraud_probs) p
   WHERE p.label = 'true') AS fraud_prob
FROM AI.PREDICT(
  (SELECT * EXCEPT(transaction_id, customer_id, transaction_ts)
   FROM `proj.fraude.transactions_rotuladas`
   WHERE transaction_ts >=
     TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 180 DAY)),
  (SELECT * FROM `proj.fraude.transactions_novas`
   WHERE DATE(transaction_ts) = CURRENT_DATE() - 1),
  label_col => 'is_fraud');

Table function para analistas e agentes

CREATE OR REPLACE TABLE FUNCTION
  `proj.fraude.score_fraude`(ini TIMESTAMP, fim TIMESTAMP) AS
SELECT * FROM AI.PREDICT(
  (SELECT * EXCEPT(transaction_id, customer_id, transaction_ts)
   FROM `proj.fraude.transactions_rotuladas`
   WHERE transaction_ts < ini),
  (SELECT * FROM `proj.fraude.transactions`
   WHERE transaction_ts BETWEEN ini AND fim),
  label_col => 'is_fraud');

Agentes via BigQuery MCP server

Gemini, ADK ou qualquer cliente MCP chama a função como ferramenta. Sem runtime de ML para operar: dados entram, previsões saem.

Antes de adotar

Custo e limitações (Preview)

Cobrança

  • Edições Enterprise / Enterprise Plus: cobrado em slots
  • On-demand: cobrado por bytes processados
  • A partir de 30/10/2026: cobrança por tokens consumidos pelo TabFM + slots/bytes do restante da query
  • Recomendação: medir total_bytes_processed e slot-ms nas execuções piloto e projetar para o volume diário

Limites atuais

  • Até 20 colunas de feature (mais: bqml-feedback@google.com)
  • Classificação em até 10 classes
  • Tipos: STRING, BOOL, INT64, FLOAT64, NUMERIC, BIGNUMERIC. Sem TIMESTAMP, ARRAY, STRUCT, GEOGRAPHY
  • Sem importância de features nativa
  • Treino grande é amostrado; para dezenas de milhões de linhas, prefira modelo treinado
  • Inferência em lote (minutos); não é endpoint online
  • Preview: termos Pre-GA, suporte limitado
